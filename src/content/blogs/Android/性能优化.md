## Profiler

### Profiler名词以及模块解释

1. RenderThread： RenderThread 是 Android 系统中的一个独立线程，专门负责执行 UI 的绘制（Rendering）和动画的渲染工作。

2. GPU Completion： GPU Completion 是 Android 图形渲染流水线中的一个关键性能指标，它衡量的是 GPU 处理完一帧所有绘制任务所花费的时间。

3. Flame Chart\(火焰图\)：是一种自上而下的可视化性能分析图表，专门用来回答一个关键问题：“CPU 时间到底被谁吃掉了？”它通过宽度表示耗时、堆栈深度表示调用关系

4. Texture upload：意思是图片首次在这一帧渲染，需要从内存上传到GPU显存。

# 性能优化方法

了解了工具的基本使用（可能也不是很了解，不过没有关系，这边建议直接让AI抓trace然后分析即可），接下来讲一下一些简单的优化思路。

在展开之前，先立一个我个人做优化时最信奉的一句话：不要看代码"应该在什么时机执行"，要看用户"在什么时机需要看到什么"。这是我在腾讯做首页游戏 Tab 冷启动优化时反复验证过的思路——把用户 0ms 就要看到的活留在主线程立即执行、把用户 100ms 后才看到的活延后、把用户完全不感知的活扔子线程，同时保证所有异步/延迟工作都可取消、可兜底。下面几节就是围绕这个核心思想展开的一些实践方法。

对不起，我没检查下来，接下来是AI总结

## 一、拆帧思想（`postDelayed` 用得好，冷启动少一半）

首先要明确一个基础事实：Android 主线程一帧的预算只有 16.67ms（60fps）。你在一帧里塞的活越多，这一帧就越可能超时，超时就是掉帧、就是卡顿。

冷启动最经典的性能问题，就是"什么东西都想在第一帧里做完"：
- 读文件缓存（IO + 反序列化）
- 各种 View inflate
- 子模块（Hippy、WebView、ExoPlayer 等）的引擎初始化
- 图片解码 + GPU Texture upload
- 埋点上报、监听注册……

这些活单独看每一件都不算重，但挤在同一帧里同步执行就会瞬间把主线程打爆。

拆帧优化就是把这些活按用户感知的优先级重新排布：

| 阶段 | 时机 | 做什么 |
|------|------|--------|
| 第 0 帧（立即）| 主线程当前帧 | 首屏必需的：Listener 注册、埋点参数初始化、内存缓存兜底 |
| 第 0 帧（立即）| 主线程当前帧 | 首屏可见组件的 View 预热（避免 bind 时白屏）|
| 子线程并行 | 子线程 submit | 引擎预热、二级模块初始化（用户完全不感知）|
| 第 N 帧（延后 100ms）| 主线程 postDelayed | 下半屏 / 非首屏内容（用户 100ms 后才滑到）|

我在游戏 Tab 里就是用这个思路把主线程耗时从 305ms 干到 20ms（↓93%）。核心动作就三个：

1. 同步 Hippy ViewPager 创建（原来 305ms 主要来源）从 `initForActive` 挪出来，改成 setData 之后 `postDelayed(100ms)` 再触发；
2. 组件预热从"post 到下一帧"改成"当前帧立即执行"（原来 post 反而导致首帧 bind 时 View 没准备好、白屏）；
3. 引擎预热扔到子线程 submit，和主线程完全解耦并行。

一句话总结：拆帧的本质不是"把慢的东西变快"，而是"把用户看不见的活挪到用户看不见的时机"。

## 二、预热思想（首屏白屏克星）

预热和拆帧是一对好搭档：拆帧决定了活什么时候做，预热决定了活在真正被用的时候是不是已经准备好了。

有几类东西是最典型的预热目标：

1. RecyclerView 的 Adapter / ViewHolder——首帧 bind 时要 inflate 一堆布局，可以在空闲帧预先 inflate 好一批 View 备用；
2. Hippy / WebView / ExoPlayer 等引擎——引擎初始化本身就是重活（JS 引擎创建 + Bundle 加载 + Module 注册），提前扔到子线程 submit 完成；
3. 网络会话 / OkHttp 连接——首个请求要走 DNS + TCP + TLS，可以在启动阶段就预建长连接；
4. 数据库 / SP——首次访问要打开文件、构建索引，可以在空闲时机 warm up。

关键坑点：预热的时机不能太早也不能太晚。太早（比如 Application 里）会拖慢冷启动，太晚（比如 onResume 里 post）又赶不上首帧使用。最靠谱的时机是"页面开始初始化的当前帧、同步走完必需路径之后、setData 触发渲染之前"这个窗口。

## 三、缓存思想（内存缓存 → 文件缓存 → 网络兜底）

用户体验对"白屏"极其敏感。冷启动 200ms 之内出现的任何白屏，用户都会立刻感觉"这 App 好慢"。缓存的核心目的不是省流量，而是消除白屏。

我推荐的分层缓存架构：

```
用户请求数据
    │
    ├─► 内存缓存命中？── 是 ──► 同步 setData（<1ms、无 IO、无线程切换）✅ 首屏立即出内容
    │        │
    │        否
    │        │
    ├─► 子线程读文件缓存 ──► 主线程 setData（走完 IO + 反序列化 ~几十 ms）
    │        │
    │        否 / 缓存过期
    │        │
    └─► 网络请求 ──► setData（几百 ms）
```

几个关键实践点：

1. 内存缓存要放在最外层。很多同学的第一版实现只有"文件缓存 + 网络"两层，但即使是子线程读文件，也至少要经过 IO + 反序列化 + 一次线程切换才能 setData，几十毫秒就没了。加一层内存缓存后，命中的场景 setData 可以做到 <1ms，白屏彻底消除。
2. 写入内存缓存的时机要早。页面 detach 时不要清、进程还活着就保留。用户高频进出同一个页面的场景收益最大。
3. 缓存和网络数据要有优先级。内存缓存渲染是"占位"，网络数据到了之后要能覆盖它，别让缓存 setData 之后又被网络 setData 覆盖导致列表抖动——通常做法是加一个 `hasNetworkData` 标记位，网络已到就跳过后续缓存回调。
4. 缓存 setData 也要做生命周期兜底。子线程读完文件回调回主线程时，View 可能已经 detach 了，一定要在子线程回调入口和主线程 execute 入口都判一次 `isAttachedToWindow`。缺一个都可能导致埋点污染大盘或对已销毁 View 做无效 setData。

## 四、图片下采样（Fresco / Glide 通用）

游戏 Tab / 电商类 App / 内容 feed 类 App 有个共性——图片元素超多，Banner、金刚位、Icon、封面图……而服务端下发的原图分辨率往往远大于 View 实际展示尺寸。

这一节我打算写得啰嗦一点，用自问自答的方式来写。因为这块我当初就是似懂非懂，只会背"下采样能省内存"这个结论，被追问一层就答不上来了。我自己真实卡住过的问题依次是：

1. 图片的"大小"和"分辨率"到底是不是一回事？下采样减的是哪一个？
2. 下采样是把图剪小了，还是缩小了？
3. 那张小尺寸的位图到底怎么来的？是从原图里取出一块吗？是压缩吗？
4. 既然这么有用，图片框架为什么不默认自己做？
5. 连框架都拿不到的信息，凭什么我们能拿到？
6. 那这个能力到底算谁的？

要把这些讲清楚，得先从最底下的"图片在内存里到底是什么"开始。

### 4.1 地基：图片在内存里到底是什么

可以把任何一张数码图片想成一面马赛克墙：整张图被切成很多小方格，每个格子里只涂一种纯色。格子足够小、足够多，眼睛看上去就是一张连续的照片。这个小方格就是像素。

所谓"一张图是 500×500"，意思就是横着 500 格、竖着 500 格，一共 25 万个格子。

电脑要记住每一格是什么颜色，需要 4 个数字：红、绿、蓝各占多少（0~255），再加一个透明度。每个数字 1 字节，所以一个格子占 4 字节——这就是 ARGB_8888。于是：

```
500 × 500 = 250,000 个格子
250,000 × 4 字节 ≈ 1MB
```

记住这个公式，它是整件事的核心：

```
解码后内存占用 = 宽（格数）× 高（格数）× 每格字节数
```

那为什么图片文件才 50KB？因为文件里存的不是"每一格的颜色"，而是一份规律说明书。

好比你要把一面马赛克墙记录下来传给朋友。笨办法是把 25 万个格子一个个抄下来，能写满一本书（这就是 1MB）；聪明办法是写"左上角一大片全白、中间一个红圆圈、右下角蓝色渐变"，一张纸就够了（这就是 50KB 的文件）。JPEG / PNG / WebP 就是不同的"聪明写法"。

但关键在这里：你朋友拿着那张纸，想真的把墙砌出来，还是得老老实实把 25 万个格子一格格铺出来。这个"照着说明书把格子铺出来"的过程就叫解码。

所以文件 50KB、解码后 1MB 一点都不矛盾——一个是说明书，一个是砌好的墙。很多人问"我图片才 50KB 怎么会 OOM"，就是把这两个混为一谈了。

### 4.2 疑惑一：图片大小和分辨率是一回事吗，下采样减的是哪个

先把三个必须分清的概念摊开：

| 概念 | 是什么 | 1080×600 的 Banner 典型值 |
|---|---|---|
| 文件大小 | 压缩后的那份说明书 | JPEG 约 150KB |
| 分辨率 | 格子数（宽 × 高）| 1080 × 600 = 64.8 万格 |
| 解码后内存 | 照说明书砌好的那面墙 | 64.8 万 × 4 ≈ 2.6MB |

文件 150KB、内存 2.6MB，差了 17 倍。压缩率完全取决于图片内容——纯色大图能压到 1/100，噪点复杂的图可能只有 1/5。所以内存里那份和文件大小基本没关系，只跟分辨率有关。

下采样动的是分辨率：

```
文件大小      150KB  ──▶  150KB    一点没变（下载的还是那份原始说明书）
分辨率     1080×600  ──▶  360×200  直接减小
解码后内存    2.6MB  ──▶  0.29MB   随分辨率下降
```

顺带说一句物理尺寸。图片文件里只有像素，没有厘米。"这张图是 5cm×5cm"是它在当前屏幕密度下渲染出来的结果（`物理尺寸 = 像素数 ÷ 屏幕 dpi × 2.54`），同一张 500×500 的图在低密度屏上可能 5cm，在高密度屏上只有 2cm。讨论解码优化时必须回到像素维度说话。

另外，既然 `内存 = 宽 × 高 × 每格字节数`，那除了砍前两项（下采样），还能砍第三项，这是一条正交的路：

| 手段 | 每格字节 | 2.6MB 变成 | 代价 |
|---|---|---|---|
| ARGB_8888（默认）| 4 | 2.6MB | — |
| RGB_565 | 2 | 1.3MB | 没有 alpha 通道，渐变处有色带 |
| Bitmap.Config.HARDWARE（8.0+）| 不占 Java heap | 像素直接放显存 | 不能 getPixel、不能做 Canvas 后处理 |

两条路可以叠加，但优先做下采样——因为改 Config 只省内存，不省解码 CPU，而下采样两个都省。

### 4.3 一张图从服务器到眼睛，要走六步

可以用点外卖来类比整条链路：

```
① 下单          代码里 setImageURI(url) / 构造 ImageRequest
      │         注意：此刻 View 通常还没 measure，尺寸未知
      ▼
② 查冰箱        Bitmap 内存缓存 ──命中──▶ 直接跳到 ⑥（最快，不用解码）
      │         未解码内存缓存 / 磁盘缓存 ──命中──▶ 跳到 ④
      │         全部 miss
      ▼
③ 送货          网络下载那份"说明书"（JPEG / PNG / WebP，几十 ~ 几百 KB）
      │         代价：网络耗时 + 无线电唤醒
      ▼
④ 拆包做菜      解码：照着说明书把格子一格格铺出来
      │         下采样唯一有意义的插入点就在这里
      │         代价：CPU 时间（正比于格子数）+ 一次性内存分配（宽 × 高 × 4）
      │         原图解码 1080×600 → 2.6MB ｜ 下采样到 360×200 → 0.29MB
      ▼
⑤ 装盘留一份    放入 Bitmap 内存缓存（cache key 里含 ResizeOptions）
      │         圆角 / 模糊等 Postprocessor 也在这一层做
      ▼
⑥ 端上桌        Bitmap ──Texture upload──▶ GPU 显存 ──采样──▶ 屏幕
                代价：上传带宽（正比于位图字节数）+ 显存占用
                GPU 采样本身几乎免费（硬件固定功能）
```

每一步的代价跟"格子数"的关系，是理解这个优化的关键：

| 步骤 | 花的是什么 | 和格子数有关吗 |
|---|---|---|
| ②③ 查缓存 / 下载 | 网络流量、等待时间 | 无关，传的是那份 150KB 的说明书 |
| ④ 解码 | CPU 算力 + 内存分配 | 有关，格子越多算得越久、占得越多 |
| ⑤ 缓存 | 内存 | 有关，占的就是铺出来那一坨 |
| ⑥ 上屏 | 内存到显存的搬运带宽 | 有关，要把整块位图真的搬进显卡 |

特别说一下 ⑥：内存和显存是两块不同的地方，数据必须真的搬过去，2.6MB 搬过去就是实打实要花时间的。System Trace 里看到的 `Texture upload` 就是这个搬运动作。

### 4.4 那么浪费到底浪费在哪

看真实场景。服务端给你一张 1080×600 的图（因为它要照顾最大的机型），但界面上那个位置只有 360×200 那么大：

```
屏幕上那块地方，物理上只有   360 × 200 =  7.2 万 个格子
你辛辛苦苦铺出来的却有     1080 × 600 = 64.8 万 个格子
```

多铺的那 57 万多个格子，一个都放不下，最后全被扔掉。但它们已经产生了实打实的开销：

1. CPU 一格一格把它们算了出来（算了）
2. 内存里给它们腾了 2.6MB（占了）
3. 还整整齐齐搬进了显存（搬了）
4. 显卡说用不了这么多，一堆格子挤成 1 格显示（扔了）

这就像：你只需要一杯水，却烧了一整壶。烧的燃气、等的时间、占的炉子，全都付出去了，最后倒掉。

而且 ⑤ 那一步还有个隐性的连锁反应：位图越大，同样容量的内存缓存能装的张数就越少，命中率被间接拉低，于是更容易走回 ③④ 重新下载重新解码——恶性循环。

### 4.5 下采样是什么，为什么它能生效

一句话：在铺格子（④ 解码）之前就打个招呼，别铺 1080×600，直接铺 360×200。

```
优化前：
  说明书(150KB) → 铺出 64.8 万格(2.6MB) → 搬 2.6MB 进显存 → 显卡挤成 7.2 万格显示

优化后：
  说明书(150KB) → 直接铺出 7.2 万格(0.29MB) → 搬 0.29MB 进显存 → 显卡 1:1 贴图
                   那 57 万个多余格子，从头到尾根本没存在过
```

三笔账同时省掉：CPU 少算约 89% 的格子、内存从 2.6MB 降到 0.29MB、搬进显存的量同比例下降。而画面看起来没有任何区别——因为屏幕上本来就只有 7.2 万个格子的位置，多出来的那些肉眼根本看不见。这是性能优化里最理想的一种：几乎纯赚。

这里顺便澄清一个我自己以前也搞错的误解：慢的不是"GPU 还得帮你缩一下"。GPU 的双线性采样是硬件固定功能的电路，快到可以忽略。贵的是前面那 57 万个白铺的格子，一路被算、被存、被搬。

还要强调"在解码阶段"这四个字，它比"下采样"三个字更重要。如果等 ④ 铺完了（2.6MB 已经躺在内存里）再 `Bitmap.createScaledBitmap` 缩一下，那基本白做：

- ④ 的 CPU 已经把 64.8 万格算完了（账付过了）
- ④ 的 2.6MB 内存峰值已经吃掉了（账付过了）
- 还额外多一次"重新铺一遍小的"的拷贝和 GC 压力（又多花了）
- 只省下了 ⑥ 那一步的搬运

回到烧水的比方：水都烧开了你再倒掉，燃气早就烧了。省钱的唯一办法是一开始就只烧一杯。

### 4.6 疑惑二：下采样是把图剪小了还是缩小了

是缩放，不是裁剪。这两件事完全不同，而且默认行为也不是裁剪。

假设原图 500×500，View 只有 100×100：

```
【下采样 = 均匀抽点，缩小】     【裁剪 = 取空间上的一块】
原图 6×6，输出 3×3              原图 6×6，输出 3×3

  ■ □ ■ □ ■ □                     ■ ■ ■ · · ·
  □ □ □ □ □ □                     ■ ■ ■ · · ·
  ■ □ ■ □ ■ □                     ■ ■ ■ · · ·
  □ □ □ □ □ □                     · · · · · ·
  ■ □ ■ □ ■ □                     · · · · · ·
  □ □ □ □ □ □                     · · · · · ·

  ■ = 保留的格子                   ■ = 保留的区域
  整张图都在，只是变粗             只剩左上角，其余内容永久丢失
```

所以"5cm 的图塞进 1cm 的位置"，默认发生的不是把图剪成 1cm，而是把整张图缩成 1cm——一根头发丝都没少，只是变小了。丢的是细节精度，不是画面内容。只有 `centerCrop` 或者手动 `Bitmap.createBitmap` 才会真的裁掉内容。

下采样做的就是把这个"缩"从 ⑥ 挪到 ④，前后显示效果一致。

唯一要留神的是 `centerCrop`：它的语义是"先缩放到刚好覆盖整个 View，再裁掉溢出部分"，需要的格子比 View 尺寸更多。

```
原图 1000×500，View 100×100，centerCrop：
  正确：先缩到 200×100（短边先覆盖）→ 再裁成 100×100
  ↑ 所以下采样目标应该是 200×100，不是 100×100
  如果按 100×100 下采样，格子不够，放大回来就是模糊
```

好在 Fresco 的 `ResizeOptions` 内部按 `max(w/targetW, h/targetH)` 算缩放比，本身就偏保守——宁可多给你一些格子，也不会给少。

### 4.7 疑惑三：那张小位图到底怎么来的，是取一块还是压缩

既不是从原图里取一块（那是裁剪），也不是解出大图再压缩，而是解码器少解一些信息，直接得到小图。具体有两种机制。

机制一：抽点 / 合并，通用做法，对应 `inSampleSize`。

`inSampleSize = 5` 的意思是原图每 5×5 = 25 个格子，在输出里只对应 1 个格子，而且是在整张图上均匀地做（就是上面那张抽点示意图）。那 25 个格子怎么变 1 个，有两种做法：

- 抽点（nearest）：直接取这 25 格里的第一个，其余扔掉。最快，但边缘可能有锯齿或摩尔纹。
- 平均（box filter）：把 25 格颜色求平均。质量好一点，多一点计算。

Android 的 `inSampleSize` 底层（Skia）主要走前者这类快速取样，所以偶尔会看到细密纹理下采样后出现摩尔纹，这是原理决定的，不是 bug。

机制二：JPEG 的 DCT 部分解码，这才是真正省 CPU 的那种。

JPEG 编码时图片被切成一堆 8×8 的小块，每块里存的不是 64 个像素颜色，而是 64 个频率系数：

```
一个 8×8 块的系数矩阵：

  左上角 ←──────────── 低频：这块的大致亮度、大轮廓
    ┌─────────────┐
    │ ●● · · · · ·│
    │ ●· · · · · ·│
    │ · · · · · · │
    │ · · · · ○ ○ │
    └─────────────┘
                 ↘ 右下角 ← 高频：细小纹理、锐利边缘
```

关键技巧：只取左上角 1×1 个系数做逆变换，就能直接得到这个块缩小到 1/8 的结果；取 2×2 就是 1/4，取 4×4 就是 1/2。也就是说那些高频系数根本不需要被解。这就是 libjpeg 的 `scale_num / scale_denom`，Fresco 对 JPEG 走的就是这条路，属于"少读 + 少算"，CPU 和内存两笔账一起省。

而 PNG / WebP 只能省内存，省不了多少 CPU。PNG 是无损压缩（DEFLATE + 逐行 filter），当前行的还原依赖上一行的结果，所以没法跳过任何数据，整个压缩流必须完整解开。它能做的是一行行解出来，但只把抽样后需要的那些格子写进目标 buffer，其余算完就丢：

```
JPEG：少读数据 + 少算  →  CPU 省了、内存省了
PNG ：数据全读 + 全算  →  CPU 基本没省，但内存省了（不用分配大 buffer）
```

这也解释了为什么 Fresco 里 PNG / WebP 的下采样默认是关闭的（要 `ImagePipelineConfig.setDownsampleEnabled(true)`）——收益只有一半，还要额外承担逻辑复杂度。

至于"是压缩吗"：不是。内存里的位图永远是未压缩的裸像素，每格老老实实占 4 字节，不存在"压缩着放在内存里"这回事。下采样得到的 100×100 位图就是 10000 × 4 = 40000 字节裸数据，它小纯粹是因为格子少了。唯一例外是 `Bitmap.Config.HARDWARE`，像素直接放显存、可能用 GPU 纹理压缩格式存储，那是另一个话题。

最后一个细节：为什么档位只能是 2 的幂。看完上面就清楚了——`inSampleSize` 官方要求 2 的幂（传 3 会被向下取整成 2），因为按 2 的幂抽点在实现上是整齐的位运算、不用插值；JPEG 的 DCT 缩放天然也只有 1/8、2/8……8/8 这些档。所以想精确到任意目标尺寸，标准做法是两步走：先用 `inSampleSize` 下采样到不小于目标的最近一档（省掉大头），再靠 `inDensity / inTargetDensity` 做一次小幅精确缩放补零头，Glide 内部就是这么干的。Fresco 的 `ResizeOptions` 更保守，只取最近一档。

### 4.8 疑惑四：这么有用，框架为什么不自己做

这是我觉得这一节最值得琢磨的问题。答案只有一句话：

在必须开始铺格子的那一刻，框架根本不知道那块地方有多大。

听起来很荒谬，不就是个 View 的宽高吗？问题出在时间顺序上。先看 Android 显示一个界面的顺序：

```
第 1 阶段 创建    把控件都造出来（此时它们全都是 0×0，没有尺寸）
第 2 阶段 排版    measure / layout：算这个多宽、那个多高、谁放哪   ← 尺寸在这一步才诞生
第 3 阶段 绘制    照着算好的位置画到屏幕上
```

为什么宽高非要等到第 2 阶段？因为很多尺寸是相对的：你写 `match_parent`，得先知道父容器多宽；你写 `wrap_content`，得先知道内容多高；而父容器自己可能也是 `match_parent`。这是一整条依赖链，必须从最外层一层层往里算。在算完之前，任何控件问自己"我多宽"，答案都是 0。

而 `setImageURI(url)` 这行代码，通常写在第 1 阶段（创建 / `onBindViewHolder` 填数据的时候）：

```
时间线：

  setImageURI(url) 执行   ←── 链路 ① 必须从这里出发
        │
        │  此刻 measuredWidth == 0，问了也白问
        ▼
  ... measure / layout ...  ←── 宽高在这里才诞生
        │
        ▼
  ... draw 上屏 ...
```

框架站在起点要往前跑（③ 下载 + ④ 解码），但"要铺多大"这个信息在后面才出现。这就是全部矛盾所在。用装修打比方：你得先去买布才能做窗帘，但量窗户尺寸这件事排在买布之后——那你买布的时候买多少？

于是框架只有两个选择，各有代价：

选择 A，干等，Glide 就是这么做的。它的 `ViewTarget` 里有个 `SizeDeterminer`，尺寸还没出来就挂一个 `OnPreDrawListener`，等 layout 结束、拿到 `onSizeReady` 再真正开工。好处是尺寸最准，代价是整条链路晚一步启动、出图晚一帧，而"首屏快点出图"往往正是你最在意的东西。

选择 B，不猜，先按原图铺，Fresco 就是这么做的。`ImageRequest` 是不可变对象，构造时就定了，pipeline 立刻启动、和 layout 完全解耦。好处是能最早开工、出图最快，代价是多铺了格子。

快和省，框架只能选一个，它没有两全其美的选项——因为信息在时间上就是不够。所以更准确的说法不是"框架拿不到"，而是"框架拿不到一个既准确、又不用延迟解码、又保证不改坏画质的尺寸"，三者不可能全要。

除了时序，就算硬要猜，框架也有三个不敢：

1. 缩了就回不去了。格子一旦按小尺寸铺出来，多的细节永久丢失。可万一用户要双指放大看？万一这个 View 在列表里被复用到了更大的位置？万一手机横过来变大了？放大一张已经缩过的图就是一片模糊。对框架来说，"慢一点"是抱怨，"图糊了"是事故，它只能选保守的那个。
2. 各存一份反而更占。⑤ 那个缓存是按 key 索引的，Fresco 会把 `ResizeOptions` 编进 cache key。如果按每个 View 的尺寸分别解码，同一个 URL 会存出 100×100、150×150、200×200 好几份，缓存被塞满、命中率下降，反而更容易重新下载重新解码。而统一按原图存一份，谁都能复用。
3. 解码器本身也做不到"精确"。前面说过档位只能是 2 的幂，所以"精确解码到任意目标尺寸"本来就不存在，只能取不小于目标尺寸的最近一档。

说到底还有一条最现实的：框架的默认行为必须对所有使用者都绝对安全。激进优化的收益归业务方，出问题的锅归框架。所以它的做法是默认保守，然后开一个口子（`ResizeOptions` / `override()`），让"我确定我这里可以缩"的人自己来说。

### 4.9 疑惑五：框架都拿不到，凭什么我们能拿到

因为我们比框架多知道三件它永远不可能知道的事：

1. 我们知道这个尺寸是稳定的。`layoutParams.width = 48dp` 这个数字框架也读得到，但它不敢用——它不知道你后面会不会改、会不会被父容器 override。而我们清楚：这个金刚位图标就是 48dp，从生到死都不会变。同一个数字，我们手里多了一份"它不会变"的保证。
2. 我们知道这张图不会被放大。框架必须防着"用户双指放大"，而我们知道这就是列表里一个展示型封面图，压根没有查看大图的交互。这个有损操作，只有业务方有资格拍板说"可以损"。
3. 尺寸就算 View 不告诉我们，也能自己算出来。Banner 写的是 `match_parent`，没排版时问不出来，但我们可以绕过 View 直接算：`宽 = 屏幕宽度 - 左右 margin`，`高 = 宽 × (设计稿 600 ÷ 1080)`。框架永远不知道你的设计稿长什么样，但你知道。

打个比方：房东不敢替所有租客改水电，因为他不知道每个人怎么用；但你自己住在这间房，清楚自家从来不用浴缸，所以你敢把那根水管改细。

这里还要分清两件很容易被混在一起的事：

- 收益来源（为什么有用）：原图分辨率远大于展示尺寸，存在冗余格子。如果服务端下发的图本来就正好是 View 尺寸，那尺寸再稳定也一分钱省不下来。
- 可行前提（为什么敢做）：展示尺寸可预知且稳定，且这张图不需要更高分辨率。前提不成立时下采样在性能上照样有效，但功能上是错的。

面试被问"你凭什么敢下采样"答后者，被问"为什么能省这么多"答前者，别答反了。

顺便说一句，尺寸不稳定也不等于必须放弃优化，只是策略要换：可以按这个 View 所有状态下可能的最大尺寸取上界（比如横竖屏都支持就按屏幕长边算，仍然远小于原图）；也可以在 `onSizeChanged` 发现尺寸显著变大时按新尺寸重新走一次 pipeline（要加阈值，别抖一下就重解）；完全不可控就退回框架原生行为。

还要清醒地认识到，客户端下采样本质上是个次优解。回头看链路图，②③ 两段（缓存 + 下载）它完全救不了——传输的一直是那份 150KB 原文件，CDN 流量和弱网首图耗时一分没省。真要连这两段一起省，只能靠服务端下发多档规格（URL 带 `?w=360&h=200`）。有条件优先推服务端，客户端下采样作为兜底。

### 4.10 疑惑六：那这个能力到底算谁的

捋清楚职责划分就明白了：

```
真正的下采样能力  →  在解码器（libjpeg / Skia / BitmapFactory）
框架（Fresco）    →  把这个能力封装成 API 暴露出来（ResizeOptions），并负责把它编进 cache key
业务方            →  提供"目标尺寸"这个唯一它才知道的信息，等于同时充当了开关和参数
```

所以框架不是"不会做"，而是"缺一个参数"。你传了它就做，不传就走原图解码。你传进去的那个尺寸，既是参数，也是你在签字确认"这里可以缩"。

几个别理解得太绝对的细节：

1. "不传就不做"只对 Fresco 成立。Glide 不传 `override()` 也会下采样，因为它选了等 layout 自己去拿尺寸那条路。
2. 传了也不一定真会缩。目标尺寸不小于原图时框架不会放大解码（只降不升）；档位只能取 2 的幂，实际生效比例往往不等于你传的值；PNG / WebP 还受全局 `setDownsampleEnabled` 限制。
3. 所以传值的心态应该是"给一个安全的上界"，而不是"给一个精确值"。传小了会糊，传大了只是少省一点，两边的风险完全不对称。

### 4.11 实践：三级降级取尺寸

以 Fresco 为例，`ImageRequest.setResizeOptions(ResizeOptions)` 就是往链路 ① 里注入尺寸信息的能力。我在游戏 Tab 里沉淀了一个通用扩展函数：

```kotlin
fun QBWebImageView.applyResizeOptions(fallbackWidth: Int = 0, fallbackHeight: Int = 0) {
    val w = when {
        measuredWidth > 0 -> measuredWidth                     // 第 1 级 已测量：最精确
        (layoutParams?.width ?: 0) > 0 -> layoutParams.width   // 第 2 级 布局尺寸固定 dp
        fallbackWidth > 0 -> fallbackWidth                     // 第 3 级 调用方兜底
        else -> return                                         // 全都无效：不动，保持原生行为
    }
    val h = when { /* 同理 */ }
    setImageSize(w, h)
}
```

这个三级降级本质上就是在逐层补齐框架缺失的那份尺寸信息，能补多准就下采样多准，补不到就不动：

1. 优先用 `measuredWidth`，最贴合真实显示尺寸；
2. 未 measure 时用 `layoutParams.width`。`setUrl` 常常在 `onBindViewHolder` 里调用，此时 `measuredWidth` 还是 0，但布局尺寸固定 dp 的场景（金刚位 icon 之类）能命中这层；
3. 前两者都拿不到时用 fallback。`MATCH_PARENT` 或运行时决定尺寸的 Banner 场景，业务方最清楚该给多大（也就是上面说的用屏宽和设计稿比例反推）；
4. 全部无效时主动 `return` 不动。这里千万别拍一个猜测值，尺寸给错的后果是图片模糊 / 变形 / 不显示。宁可不优化，也别把功能改坏。

Glide 的对应能力是 `override(width, height)`，因为它默认走"等 layout"路线，所以更多用在非 View target 或需要显式控制的场景；但只要是解码时机早于 measure 的链路，要解决的本质问题完全一样。

收益：图片解码内存显著降低、Texture upload 带宽和解码 CPU 时间同步下降，通常能直接贡献首帧耗时 10~30ms 的下降。

### 4.12 收束成三句话

1. 为什么有用：多铺出来的格子，被算、被存、被搬，最后全扔了。不铺，这三笔钱一起省。
2. 为什么必须在解码时做：铺完再缩，钱已经花了，等于白做。
3. 为什么框架不做：在必须开工的那一刻它不知道该铺多大——要么等（出图变慢），要么猜（可能糊图）。它只能选对所有人最安全的默认值，把口子留给确实知情的业务方。

而我们能做，是因为我们掌握着框架看不到的信息：这个位置多大、这张图会不会被放大、设计稿是什么比例。性能优化很多时候就是这样——不是找到了什么黑魔法，而是"我知道一些通用框架不可能知道的前提，所以我能安全地砍掉它为了保险而保留的那部分开销"。

## 五、生命周期防御（性能优化最容易翻车的地方）

性能优化引入的大量子线程任务、延迟任务、Listener 注册，如果不做生命周期兜底，就是内存泄露 / 崩溃 / 埋点污染的高发区。总结几条我认为必须做的防御：

1. 所有子线程任务用 `submit` 拿 `Future`，存成员变量，`onDestroy` 时 cancel。

```kotlin
private var hippyPreloadFuture: Future<*>? = null
private var cacheReadFuture: Future<*>? = null

// 使用
hippyPreloadFuture = executor.submit { preloadHippyEngine() }
cacheReadFuture = executor.submit { loadAndApplyCacheData(startTime) }

// 生命周期结束
fun unregisterListeners() {
    hippyPreloadFuture?.cancel(true); hippyPreloadFuture = null
    cacheReadFuture?.cancel(true); cacheReadFuture = null
}
```

为什么必须 cancel：任务持有 View 引用会内存泄露；回调回到已 destroy 的 View 上会 crash；detach 后继续跑的埋点会污染性能大盘。

2. 所有 `postDelayed` 的 Runnable 要能取消。

```kotlin
delayUpdateViewPagerRunnable?.let { removeCallbacks(it) }  // 防止 setData 短时间多次调用重复投递
delayUpdateViewPagerRunnable = Runnable { ... }
postDelayed(delayUpdateViewPagerRunnable, 100L)

// detach 时清理
addOnAttachStateChangeListener(object : OnAttachStateChangeListener {
    override fun onViewAttachedToWindow(v: View) {}
    override fun onViewDetachedFromWindow(v: View) {
        v.removeCallbacks(delayUpdateViewPagerRunnable)
        v.removeOnAttachStateChangeListener(this)  // listener 自解绑
    }
})
```

`Handler.postDelayed` 持有 View 引用是 Android 里的经典内存泄露源，必须做这层清理。

3. 子线程回调入口和主线程 execute 入口都判 `isAttachedToWindow`。

```kotlin
loadGetFeedsNative { data ->
    if (!isAttachedToWindow) return@loadGetFeedsNative   // ★ 兜底 1：子线程回调入口
    // ... 数据处理 ...
    mainExecutor.execute {
        if (!isAttachedToWindow) return@execute          // ★ 兜底 2：主线程回调再兜一次
        setData(data)
    }
}
```

双重兜底——因为子线程判断和主线程执行之间可能又发生了 detach，只判一次不够。

## 六、跨端场景（Hippy / RN）的额外考量

如果你的页面是 Hippy / React Native 之类的跨端框架，除了 native 的通用优化之外，还要多考虑一件事——JS 侧与 native 侧的过桥调用（bridge call）本身就是耗性能操作。

我在游戏中心 hippy feeds 遇到过一个非常典型的案例：

问题现象：feeds 长列表连续点下载按钮，越点越慢。总数六百多个按钮时同款只有 1 个时约 30ms 很流畅；但按钮总数不大、同款存活 13 个时要 477ms，明显卡。

排查过程：一开始直觉是"列表太长按钮太多"，但加了埋点量化之后直觉被推翻——卡顿只和"同款重复存活的实例数"强相关，和总数无关。顺着日志继续挖，发现一次下载状态变更被展开成 N 次界面刷新、N 次过桥调用、N 条重复上报。

根因：同一款游戏在 feeds 里出现多张卡片，每张卡片都各自向底层挂了一个下载状态监听。列表滑动时旧卡片并不销毁（因为 hippy 的 recycler 语义），监听持续累积。底层只发一次变更，却触发 N 次过桥回调。

解决方案（只改状态分发链路、不改下载业务逻辑）：

1. 按 url 维度共享监听——同一款游戏只向底层注册一次监听，多张卡片只是登记为订阅者。N 次 `addDownloadStatusListener` + `startWatchDownload` 过桥被砍成 1 次。
2. 合并中间态——进度事件做节流（固定间隔刷新一次）；中间态进入一个短暂合并窗口只保留最终态；最终态立即分发保证"点了有反应"。
3. 消除竞态——取消下载的最终态由前端主动确定，同步终态前先清掉合并窗口里残留的中间态，避免刚设好的最终态被覆盖。
4. 界面侧再去一次重——一次刷新算出的状态和进度与当前完全一致就直接跳过，不做无效刷新。

收益：一次操作从 N 次昂贵过桥"集中爆发"收敛到常数级，同款游戏存活数量再大也不再卡顿。

这个案例的方法论收获：

- 直觉不可靠，一定要加埋点量化验证——"列表太长"这个直觉如果没被日志数据推翻，就会走错方向去做虚拟化优化，然而虚拟化本来就已经做了、根本救不了这个问题。
- 跨端框架的性能瓶颈往往在 bridge 层——不是每次 render 慢、也不是 JS 执行慢，而是JS 和 native 之间的通信次数太多。类 RN 跨端框架性能相比于 KMP 等直接生成编译产物的框架稍差的核心原因也在这里。
- 优化跨端页面时，先看 bridge call 数量，再看 render 次数，最后才看单次执行耗时——这个优先级搞反了会白忙一场。

## 七、上报 / 埋点类高频请求的批量优化

这一块其实不算传统意义上的"渲染性能优化"，但它直接影响用户体感的两个核心指标——发热和续航。做客户端性能优化如果只盯着 FPS 不看这两个，用户仍然会觉得"这 App 用久了烫手、掉电快"。

以广告 SDK 的数据上报为例，信息流场景下用户每滑一屏，一次广告请求可能触发 3 次上报、广告加载又有 2 次。用户滑动几分钟，几百上千次网络请求就出去了。每次都是独立的 HTTP 请求，看起来"每个请求都很小、应该不影响什么"，但底层的实际代价触目惊心。

解决方案很简单——SDK 内部缓冲 + 窗口批量发送。比如攒够 20 条或者静默 2 秒就 drain 一次。表面看请求数没变（10 次上报还是 10 条数据），但底层的物理代价完全不同。

要理解为什么"先攒后发"能省电，就要理解 Android / 移动设备的三个底层物理特性：

### 7.1 蜂窝网络的 RRC 状态机

以 LTE/5G 为例，无线电模块（Radio Resource Control）有三个核心状态：

```
IDLE  ──唤醒（100ms~2s，高耗电）──▶  CONNECTED（高功耗、全速传输）
                                          │
                                          │ 数据传输完成
                                          │ 保持 5~15s tail time（仍高功耗）
                                          ▼
                                        IDLE
```

三个关键特性：

1. 唤醒有代价：IDLE → CONNECTED 需要信令交互，耗时几百毫秒到 2 秒，功率瞬时可达 1000~3500 mW；
2. Tail Time（尾部功耗）：数据发完后无线电不会立即回 IDLE，会保持高功耗态 5~15 秒等待后续数据；这段"空转"白白耗电；
3. BatteryStats 归因：Android 会记录 `mobile_radio_active_time` 并归因到具体 App，是 Google Play / 手厂"耗电异常检测"的核心指标——你的 App 会被系统显示"耗电异常"，用户看到就会卸载。

### 7.2 Wi-Fi 的 PSM（Power Save Mode）

Wi-Fi 芯片有类似的省电机制，但代价小一个数量级：

| 维度 | 蜂窝（LTE/5G）| Wi-Fi |
|------|--------------|-------|
| 空闲→活跃唤醒耗时 | 100ms ~ 2s | 1~10ms |
| Tail time | 5~15 秒 | ~200ms |
| 唤醒瞬时功率 | 1000~3500 mW | 50~200 mW |
| 是否记入 BatteryStats | ✅ | 权重低 |

### 7.3 CPU 深度睡眠

现代 SoC 的 CPU 支持多级 C-state：

- C0（Running）：满载功耗 3~5 W
- C1~C5：浅睡眠，可快速唤醒
- C6+（Deep Idle）：整机功耗可低至 300 mW，需要 10~20s 无扰动才能进入

每次 `socket write + TLS encrypt + response parse` 都会强制 CPU 进入 C0，阻止 CPU 进入深度睡眠。这是移动端"App 在后台仍然发热"的核心机制。

### 7.4 TCP / TLS 握手代价

即使有 HTTP Keep-Alive，仍会因为以下场景反复重连：

- NAT 表超时（家用路由器 30~60s）
- 服务端 idle timeout
- 移动网络切换 / AP 切换
- OkHttp 默认连接池仅 5 条，高并发下触发新建

单次重连代价：TCP 3 次握手 (1 RTT) + TLS 握手 (1~2 RTT) ≈ 100~300ms 网络耗时 + 5~15ms CPU 时间（非对称加密 RSA / ECDHE 开销）。

### 7.5 收益量化（以蜂窝 × 低频上报为例）

假设每 30s 上报一次、共 10 次：

未优化（10 次独立唤醒）：

```
每次上报：IDLE ─唤醒(1s)→ CONNECTED ─发送(0.5s)→ tail(10s) → IDLE
每次高功耗时长 = 11.5s
────────────────────────────
无线电高功耗时长 = 10 × 11.5s = 115s
无线电耗电 = 115s × 1500mW ≈ 48 mWh
RRC 唤醒 10 次，TCP/TLS 握手约 4 次
```

优化后（1 次批量）：

```
10 条聚合成 1 批：IDLE ─唤醒(1s)→ CONNECTED ─连发10条(1s)→ tail(10s) → IDLE
高功耗时长 = 12s
────────────────────────────
无线电高功耗时长 = 12s
无线电耗电 = 12s × 1500mW ≈ 5 mWh
RRC 唤醒 1 次，TCP/TLS 握手 1 次
```

| 指标 | 未优化 | 优化后 | 节省 |
|------|--------|--------|------|
| 无线电高功耗时长 | 115s | 12s | ↓89.6% |
| RRC 唤醒次数 | 10 | 1 | ↓90% |
| TCP/TLS 握手 | 4 | 1 | ↓75% |
| 总耗电（单周期）| ~48 mWh | ~5 mWh | 省 43 mWh ≈ 0.28% 电量 |

单次批次省 43 mWh 看着不多，若一天有 200 个这样的上报周期，累计可节省 ≈ 8600 mWh ≈ 55% 一整块电池。这就是为什么 Android 官方文档反复强调 "batch network requests"。

### 7.6 四象限总结（蜂窝 / Wi-Fi × 高频 / 低频）

| | 低频（30s/次）| 高频（300ms/次）|
|---|---|---|
| 蜂窝 | 场景 A：RRC 收益最大，节省 ~90% 无线电时长 | 场景 B：RRC 收益消失（tail 永远不结束），CPU 收益接管，仍能省 ~13% |
| Wi-Fi | 场景 D：绝对量小但相对收益高，副作用为零 | 场景 C：CPU 收益接管，仍能省 ~76% 无线电耗电 |

几个关键洞察：

1. 高频场景 RRC 收益消失——因为 tail time 永远不会走完，无线电根本没机会睡。但CPU 收益接管了主导地位——批量后 CPU 只需要间歇性唤醒，其余时间可以进入 C6+ 深度睡眠。
2. Wi-Fi 场景的绝对节省电量甚至可能超过蜂窝——因为蜂窝下 CPU 收益被巨大的无线电耗电所掩盖，Wi-Fi 下 CPU 收益反而是主角。
3. 低频 × Wi-Fi 是最不迫切的场景（绝对量极小、用户完全无感知），但副作用为零——不需要为它单独关闭优化，统一策略即可。

### 7.7 用户体感对比（视频/直播 30 分钟）

| 观感指标 | 未优化 | 优化后 |
|---------|-------|--------|
| 手机后盖温度 | 36℃ → 43℃ | 36℃ → 38℃ |
| 电量消耗 | ~12% | ~9% |
| Wi-Fi 状态 | 偶发"网络繁忙" | 流畅 |
| 用户吐槽率 | 高 | 无感知 |

这里体现的是"批量上报"最直接的用户价值——不烫手、不掉电。这两点比任何 FPS 指标都更容易被用户直接感知。

### 7.8 为什么"先攒后发"永远优于"均匀分散"

批量上报优化能生效，是因为它同时命中了移动设备的三个物理特性：

- 无线电模块"唤醒贵、传输便宜"——减少唤醒次数即节省电量；
- CPU"深度睡眠功耗断崖式下降"——减少唤醒次数即让 CPU 有机会真正休息；
- HTTP 协议栈"每次请求有固定加密 / 序列化 / 系统调用开销"——减少请求次数即节省 CPU 时间。

在性能监控 / 广告上报这种"高频、可延迟、单条不关键"的业务特性下，这三层收益可以被完整拿走，而几乎不需要付出任何代价。

这就是为什么同样是 10 次请求，"合并在一个窗口内发出"永远优于"均匀分散发出"——不是网络省了，而是整个系统链路都获得了休息的机会。
当然批量上报将10次请求最终合成为一次请求才是最佳实践，上面只是在说明如果没有合并的能力那这么做其实也是有意义的

## 八、性能优化的方法论收束

写到这里，其实几节讲下来会发现——所有的性能优化归根结底都在做同一件事：让用户能立刻看到他关心的东西。

我个人总结的性能优化几点：

1. 这个活能不能不做？（最快的代码是不执行的代码）
2. 这个活能不能延后做？（拆帧 / postDelayed）
3. 这个活能不能在别处做？（子线程 / 预热）
4. 这个活能不能做得更小？（图片下采样 / 批量上报）

每一次做优化之前，把这四个问题挨个问一遍，通常都能找到方向。

还是那句话，性能优化就是提升用户体验，哪怕你CPU干到90，但是都是异步任务，用户在UI界面看起来很流畅，那就是好优化，反之你拆了n个帧，create拆出来，bindData拆出来，上屏再拆出来，虽然CPU一直很低，但是用户看起来上屏慢，这就不是好优化，上面的例子比较极端，高CPU往往意味着高耗能高发热，只是想说这样一个道理

最后一句忠告——性能优化最容易翻车的不是"没优化到位"，而是"优化引入了新问题"。所有的异步、延迟、缓存、批量，都必须配上完善的生命周期防御；所有的收益数字，都必须配上准确的埋点验证。做到"优化能被量化、稳定性有兜底"，你才算真正把这件事做好。
